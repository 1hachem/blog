Agentplace, through a new user's eyes

Hachem Betrouni · product review · October 2026 · 2 days, 4 agents, 13 builder sessions
TL;DR
  • The builder kept talking about its own plumbing. I also couldn't tell what Agentplace does for me, and no one showed me around.
  • Fix first: a builder that speaks outcomes, guarded by a no-leak eval in CI. One metric: the % of replies a non-technical owner understands.
  • Under the hood, every agent runs its whole stack in dev mode, and login tokens sit in a WebSocket URL. Seven nitpicks, each with a one-line fix.

How I made this report. I used Agentplace as a new user for two days, building 4 agents across 13 builder sessions. Everything marked is that experience, in my words. Then I pointed AI agents at it : a browser agent read the network, console and JS bundles to identify the stack, and I pulled all 13 builder conversations through the app's own API to count errors and jargon. The three biggest problems

I came to build a chatbot and left knowing three connection pools by name. I didn't want a pool, I wanted a receptionist.

1It talks to me about its plumbing

“Pools, workers, roles, "build is clean, 0 warnings". My Linear connection landed in the wrong pool, and I had to log in again.”

27 of 43 builder replies used internal terms.
Fix: spec 001, next page.

2It never tells me what it does for me

“The landing page is clean, but I couldn't tell whether it was for me. The hero examples are one-off vitamins: a Lake Como trip, a hotel room.”

7 of my 13 sessions were "what can you do?". Only 3 built something.
Fix: painkiller workspaces, salons first (spec 002).

3No one shows me around

“No onboarding. Templates can't be reached in the app, Pro models are pickable on free, and credits don't say what they buy.”

My first build ran 10m45s showing 100+ raw tool steps.

I asked for a CV. Three rounds later I had a gorgeous welcome screen and the confidence of a man with no CV.

How I'd prioritize

  1. Plumbing: every user hits it in every reply, it makes the other two problems worse, and an eval can guard it.
  2. What it does for me: painkiller workspaces get the right users to the first request.
  3. Orientation: copy and UI quick wins that ship alongside.

A builder that speaks outcomes

Branch 001-plain-language-builderCreated 2026-10-25Status Draft

Input: "A non-technical owner should understand every builder reply and know what to do next, without learning how Agentplace works inside."

User Scenarios & Testing
P1Replies in outcome language

The owner asks for a change. The builder reports what changed for their business and what to try next. No pools, workers, roles, builds or tool names.

Why this priority: it reaches every user in every reply. 27 of my 43 builder replies used internal terms.
Independent test: replay the eval set of real first sessions, and the judge scores every builder reply.

  1. Given a task that needs Linear, when the builder connects it, then it says "Linear is connected, only you can use it", not "connected to the team pool".
  2. Given a finished build, when the builder reports back, then it says what customers can now do, not "the build is clean, 0 errors and 0 warnings".
  3. Given a tool step that fails and is retried, when the turn ends, then the owner never sees the raw error.
P2Progress in phases, not tool logs

Researching → Building → Testing → Ready, with the elapsed time. Raw tool steps sit behind "details".

  1. Given a turn longer than 30s, when a phase changes, then a one-line, plain status updates.
P3The platform picks the plumbing

Where a connection lives is inferred from the task, with at most one plain question.

  1. Given a private task, when a service is connected, then the public app can't use it, and the owner wasn't asked to choose a pool.

Edge cases: asked "how does it work?" → answer technically. Technical users → "details" on demand.

Requirements, entities & assumptions

Functional Requirements

  • FR-001 Builder replies MUST describe the outcome for the business and a next step, not internal mechanisms.
  • FR-002 System MUST map internal concepts to plain names: team pool → "private to you", agent pool → "used by your public app", worker → "a helper that runs on a schedule".
  • FR-003 System MUST collapse tool steps into four phases and hide raw errors and retries by default.
  • FR-004 System MUST decide a connection's destination from the task, asking at most one plain question.
  • FR-005 A no-leak eval MUST run in CI on every prompt or model change and block a release that lowers the score.
  • FR-006 The judge MUST run as a PostHog LLM-as-a-judge evaluation over the captured builder replies.

Key Entities

  • Glossary entry: an internal term and its plain name.
  • Eval scenario: a replayed first session plus the outcome the owner wanted.
  • Judge verdict: understood? next step clear? internal terms found?

Assumptions

  • The replay set starts from real first sessions, used with consent.
  • The judge uses a different model family than the builder.
  • Power users keep "details".

Success Criteria

SC-001: the comprehension score, the % of builder replies the judge rates "a non-technical owner understands what happened and knows what to do next". Target 90%+ on the replay set before shipping. Baseline likely under 40% (63% of my replies had internal terms).

Architecture at a glance

Everything enters through one CloudFront distribution. The marketing site and the dashboard are static files on S3. /api goes to a Node/Express API behind nginx that handles Cognito auth, Composio connections and the builder chat over a WebSocket. The builder is an AI SDK agent loop across four model providers, traced in Langfuse. Each agent you build is a separate app, a Node agent server plus its own React frontend, reached through a wildcard *.run.agentplace.io router on EC2 with no CDN in front.

What already works well: the builder is honest about what it hasn't tested. It cut my PostHog access down to read-only tools on its own, and refused both of my prompt-extraction attempts. The EU cookie banner is done right. The marketing site is a clean static build with JSON-LD and llms.txt.

The biggest nitpicks

Every agent starts its whole stack

Each agent boots its own Node server and React frontend in dev mode: a 5MB unminified bundle, livereload and a build server, even though most agents differ only in config, prompts and UI components.

Fix: One shared, production-built runtime that loads each agent's config by subdomain. Build per agent only when it ships custom code.

An LLM call every time a preview opens

Opening a preview runs a ~17k-input-token turn just to draw the greeting. All of it is cache writes, with zero cache reads.

Fix: Cache the first screen per agent version, and call the model only when the visitor writes.

Chat history downloaded twice

Each dashboard load sends the same 988KB history query twice. The second one doesn't pass afterSeq.

Fix: Load once, then fetch only new items. Lazy-load tool details when they're expanded.

Login tokens in the WebSocket URL

/api/dashboard/ws?token=…&idToken=… puts the Cognito access token and the 24h ID token (name, email) into CloudFront and nginx access logs.

Fix: Use cookies, which the builder socket already does, or a 30-second one-time ticket.

Model reasoning sent to the browser

The UI hides it, but the history payload carries the model's third-person notes about "the owner".

Fix: Strip reasoning server-side before it leaves the API.

Tracking without a banner outside Europe

From Algeria, ~520KB of trackers load on first paint, including the session-replay setup. In the EU the banner works, but an Amplitude cookie is still written before consent.

Fix: Load replay and pixels only after consent, everywhere. Proxy events through agentplace.io/ingest behind the gate.

Nobody onboarded me as a user, but the console onboarded me as an engineer: debug logs, a red 401, WebSockets opening left and right, "Unknown notification" on every turn. Day one and I'm already on call for the dev server.

Dev noise in production

Logged-out visitors see debug logs and a red 401 on every visit. The preview runs a React development build, prints connection chatter and "Unknown notification" on every turn, and streams its server logs twice over SSE, including the owner's email. Express is advertised with x-powered-by.

Fix: strip logs at build time, treat the expected 401 as a quiet state, use one SSE connection, and ship production builds to previews.
