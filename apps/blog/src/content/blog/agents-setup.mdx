Since absolutely nobody asked me how I use my coding agents, here I am writing a blog in detail about it.

Lately while developing [lisptc](/blog/lisptc) - a neuro-symbolic language and AI harness, find it at [github](https://github.com/1hachem/lisptc) - I decided to fully build it with coding agents,
no handwritting code.

**BUT** that doesn't mean that I am going to follow the vibe-coded app path where I prompt for features and let agents do whatever they do these days,
instead it's going to be **I think, I design, you code**.

Giving up code completely to agents meant that I have to make sure to set up the right coding harness and develop the right tools that would keep things under control,
I didn't want to end up 2 months down the line with a mess that no one can debug,
not even the agents that built it.

The thing is that one bad practice in your code is the context for the next agent, which is going to follow the same bad practice +1, this is the failure mode that most vibe coded codebases usually fall into, thinking that agents are immune to **technical debt**.

The name of the game is how can you detect, illustrate, visualize and then reduce technical debt.

## Dashicodes a dashboard to visualize technical debt

Scripts catch a rule the moment it breaks, but technical debt doesn't break anything, it accumulates, a file that gets a little hairier every week never fails ci, so I built a dashboard for lisptc
whose only job is to show me the shape of the codebase and how it is moving.

The app runs its own analysis using different tools like `fallow`, `git` and `gh` github cli, it draws:

- **hotspot quadrant**, prioritize refactors
- **layered dependency graph and DSM**, spot layer violations
- **import cycles**, reveal circular dependencies
- **temporal coupling arcs**, uncover hidden coupling
- **blast radius per pull request**, assess change impact
- **pull request flow and lifetimes**, track progress and bottlenecks

I can compare results over time to see the progress.

## Test driven refactors

<Callout variant="failure">

**A working feature can hide a fragile implementation.** An agent can satisfy the request while adding workarounds and coupling that make the next change harder. A later refactor can also change behaviour I already liked unless tests protect it.

</Callout>

As I develop the product, I ask an agent to add a new functionality, I describe how it has to work, the agent goes and builds it, I don't care how, we iterate, I test the feature, modify it, once I like it, I commit to it by asking for tests that the feature passes, now I turn my eye to the implementation, I ask the agent to brief me about its changes and how it works and all the workarounds it used, I ask it to vizualize it for me, I read some parts of the code,
I then propose a better design, an architecture choice, a technology choice, the right abstraction and the refactor work starts, we have the tests as guidelines that the refactor didn't change the feature.

## Forbid comments and dev docs, they are obsolete

Code is the only source of truth, this means less context for the agent to read, if the agent needs certain details about the implementation it has to read the code.

<Callout variant="failure">

**Comments can claim behaviour the code never implements.** An agent can describe the intended functionality in a comment and leave the actual work incomplete. Even an accurate comment can drift after a change, and the next agent may trust it instead of checking the code.

</Callout>

Comments are made for humans since they can't hold enough in working memory, agents don't need comments

How I enforce this in the codebase:

- `no-comments` script that strips all comments and fails ci in case there was an added comment

- rule in top level AGENTS.md that forbids comments

- a whole codebase with no comments, agents tend to follow the convention of the code they read

I pulled that script out into its own repo, [no-comments](https://github.com/1hachem/no-comments), it walks the ast instead of grepping, so a `//` inside a string is left alone, and it comes in both shapes, a github action that fails the build and posts the removal as a pr suggestion:

```yaml
- uses: actions/checkout@v4
- uses: 1hachem/no-comments@v1
```

and a binary you hang on a pre-commit or pre-push hook so the comments never land in the first place:

```bash
pnpm add -D github:1hachem/no-comments#v1
no-comments --staged --fix
```

## No implementation details in `AGENTS.md`

<Callout variant="failure">

**Documentation drifts, then becomes misleading context.** An agent changes the code but leaves an old explanation or file path behind. The next agent follows it, starts from the wrong assumptions, and can build more mistakes on top. Longer docs also bury the few pointers it actually needs.

</Callout>

This one is a bit tricky to enforce since llms love wasting tokens rambling about implementation details, I never read the docs the agent writes, instead I ask an agent to go and produce an interactive artifact about how something works, data flow, dependency, pros, cons and tradeoffs

Dev docs become **just-in-time**, generated directly from the code and scoped to what you need to know. In five minutes you have an interactive HTML page with illustrations of the data flow, module relationships and tradeoffs, so you can explore how things fit together. A fresh explanation when you need it, without maintaining separate docs that keep growing, drifting and misleading your agents.

So what is left in these files is a map, `AGENTS.md` files become routers, every workspace carries its own and lists where things are found. The agent lands on the root file, finds the workspace it needs and goes straight to the relevant code.

<AgentsRouters />

The root file holds only what is true repo wide, the rules that no single package owns. Things like dependency direction, keeping external effects behind interfaces, decoupling modules, centralizing typed configuration, and keeping tests with the package that owns the behaviour. Even small conventions count, like using one icon library or carrying no comments.

The exact choices depend on the project, the point is to make them enforceable. An agent can break any of these rules in a single line, and a script should catch it in ci. That is the bar for putting a rule in the root file, with a pointer to where it is enforced. Package-specific details stay in the code, and the package's `AGENTS.md` points there.

In ci I make sure that any change to `AGENTS.md` is only a pointer toward what is there, not how it works and implementation details, by running jev classification on each hunk of change.

## Boundaries and dependencies

<Callout variant="failure">

**A local shortcut can break the architecture.** An agent reaches across a module boundary to get a feature working, introducing coupling or a circular dependency. The feature can still pass its tests while the codebase becomes harder to change.

</Callout>

I decide which parts of the codebase can depend on which, then make those boundaries part of the checks an agent runs. This keeps modules decoupled as new features land.

In lisptc I use Turborepo's boundary checks for this, along with custom checks for rules it cannot cover. They run in ci and before pushing, so a dependency that breaks the architecture fails a check.

## Closing the loop with traces

I use real usage and user reports to decide what needs improving. In lisptc, for example, I collect conversations using [PostHog](https://posthog.com/) and have scouting agents look for recurring problems.

Sometimes I review those traces myself. They show where users get stuck and give me concrete cases to bring into the next round of feature work, tests and refactoring.

## Check for code duplication

<Callout variant="failure">

**Agents can duplicate logic instead of finding what already exists.** A slightly different request gets a slightly different copy of a function. Now a bug fix has to reach every copy, and the versions start drifting apart. Replacing an implementation can also leave the old one behind as dead code.

</Callout>

Using tools like [fallow](https://fallow.tools/) you can detect code duplication and dead code, these can be your signals for better abstractions and shared logic.

Having scouting agents that occasionally kick off and look for these opportunities automates most of this, however it stays important to keep an eye on the code and try to find these yourself.

## Less technical debt means better agent code

<Callout variant="failure">

**One workaround becomes the next agent's example.** Allow a cyclic import once and patch around it, and a later agent **will** copy that solution elsewhere. A temporary exception becomes a convention through repetition.

</Callout>

Clear architecture and good design patterns are the signal your agents copy, and so are the bad ones. That is why I keep checking the shape of the codebase even when the features work and ci is green.

Follow the right design patterns, respect convetions in your code, create interfaces and decouple your modules, follow good file hygenes and your coding
agents will follow.
