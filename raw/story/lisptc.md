Anthropic’s blog post about programmatic tool calling shed light on a better way to use ai agents, instead of calling tools in a loop the agent becomes a programmer that writes function calls and logic in a language of choice.

This is particularly useful since
1- it consumes less time and tokens in the sense that it doesn’t require extra boilerplate tokens like the ones that come with json schema, doesn’t require a system prompt of the tools schema + you can use it inside for loops instead of relying on the model to call multiple ones + you can use variables to store data and pass it without loading your context and so on. The only downside I can think off this approach presents security concerns, first the code the agent executes can be malicious in many ways, the user may want it to be, a prompt injection may occur or the agent can write code that never stops consuming host resources. This well known problem of untrusted code execution will lead you down a rabbit hole of years of work on sandboxing and isolation, however this is still a standing problem that is only mitigated and the current solutions will increase the complexity of your solution considerably. The problem is that trying to limit the power and access of a general purpose programming language is a hard task and there is always workarounds. However there is another way of doing exactly that and it’s to build a language from the ground up without the extra access you don’t want. When vercel (Fuck you vercel) announced that they built .0 a language destined for AI agents I was excited, I hoped they optimized for prompt usage, built a language around 0 trust permissions, and builtin memory or mcp support, instead it was a big flop a side project that the marketing team made a big deal of. No one i know of built what I needed so I went out of my comfort zone and started reading about interpreters and programming language design, at the entry was the perfect language for my use case. LISP! First developed in 1950 for AI research purposes, the ideas behind lisp went on to influence most of today’s programming languages, notoriously known to making better programmers. The ideas behind lisp seemed compelling: ⁃ What is the simplest way to build a syntax less language ⁃ What are the minimum number of irreducible primitives to use ⁃ REPL workflow is perfect for AI agents Make a lisp, mal in short, an open source project of building lisp interpreters in different languages: C, js, python, go, you name it The C implementation of the interpreter had 500 lines, I was in owe, I knew I can fit the while interpreter in a system prompt the agent could learn the language inside out. I went in and built a lisp interpreter with an in memory REPL that I hooked to PI agent. At first I just cloned an implementation of the interpreter in typescript and went on modifying it with claude code. We needed a language sever which turned to be fairly easy to build with vscode-language-server, we needed a formatter, topiary was there to help us with a spec driven formatter, everything packaged in a nix flake I was impressed by how easy it was to build a language, a formatter and an interpreter, all thanks to the genius design of lisp The best part was that I can easily constrain the model output to the lisp syntax, llama.cpp uses gbml format through which you can describe the language grammer and generation rules, pass this in with your api call and the model can only output a token that satisfies your grammer. Not all models allow for this only the opensource ones and not all providers have this passthrough, i can only name few that have it: fireworksAI Maybe at some point I will have to self-host these AI models. I didnt touch jupyter notebooks from the day I switched careers from an AI engineer to a software engineer, and I just forgot how much the repl model is amazing, you debug code and test it as you write it, the repl keeps the context and provides feedback, this model is fantastic for AI agents, the agent gets instant feedback, it was trained on this kind of execution with all the notebooks in it’s training data. I was impressed as well by how easy it was to setup my editor with my custom formatter, lsp and repl, providing an adequate workbench to tear and assemble these scripts. The well thought of and minimalistic by default and easily extendable nature of the PI agent framework made it easy to have a chat tui connected to my repl on the get go. The last missing piece of this is a cognitive architecture that combines the power of llms with the symbolic nature of my language, this is going to be a separate memory module that extends the interpreter. Another feature that was really easy to implement was a native mcp integration, you load an mcp (stdio or online) by calling ‘(await load-mcp)’ (notice the async support so tasks can be scheduled or awaited) once it loads all the mcp tools will be available as a function (lsp support as well since the repl is shared with the editor and the lsp). Discoverability functions are added as well, to search for predefined mcps servers and to find tools from within a loaded mcp. This is progressive disclosure native instead of it being an afterthought bolted in. Another perk of owning the interpreter and the repl is the ability to implement context compression from the get go, each variable can only be read with grep like commands, and the result comes paginated by default, in other words the llm can read exactly what it needs to. This is especially helpful when working with browser automation using playwright mcp, most of the time a snapshot of the web page comes with a bloated styling, JavaScript and html, often leading to pollute the context and get us near the 30% dumb zone in few turns (if not one). Generative ui, visualization of the lisp prelude and the execution One last cool feature worth mentioning is the availability of read only variable that contains the whole conversation messages that the agent can use in order to extract input from (think of a long number that the agent using an open-source model will surely hallucinate mid way). This is just the tip of the berg, at this point anything you can think of that is needed to build an AI agent around llms can be implemented neatly in this system, the llm is not the agent its part of a system where every module plays a role to reach an objective, best thing is to leave the imaginary, creative and flexible parts to the llm and the rest to the symbolic system (the lisp), just like how the brain has 2 hemispheres. This is still work in progress my objective is to benchmark this cognitive architecture against its counterpart “harnesses” (I prefer cognitive architecture over harness since the term is deeply rooted and one can draw from decades of research, instead of AI harness which is the new kid in the block). One of the biggest fears I had with this approach was, drum roles ….. the parentheses, i was afraid that open models will always mess up the syntax of lisp, in the end big portion of the code bases modern languages js and python, I was impressed by how well the proprietary models did when the while interpreter was in the system prompt, or by how the open models did when the output was constrained with the lisp grammar. At first claude at least made one mistake before fixing the tool calls to lisp repl, but with interpreter in system prompt, things were smooth. The whole project was generated with coding agents, tests turned out to be straightforward, you write lisp code and expect it to do what it says.
